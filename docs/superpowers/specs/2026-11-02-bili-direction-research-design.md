# B 站「方向研究」工具设计（research.mjs）

- 日期：2026-11-02
- 状态：已获用户口头批准，进入实施
- 目标用户：用户（手机端 QQ / Web，一句话提问，例如「最近显卡价格怎么样」）

## 1. 问题与目标

现有 `bilisum.mjs` 解决的是「给一条链接 → 出一份速读稿」。用户的新需求是**给一个方向 → 自己去搜、去看、给结论**：

> 「用户给你一些方向，你去 B 站搜索相关视频，然后进行观看，观看后给我这方向的结论。」

因此本工具要补齐**检索 → 筛选 → 批量取素材 → 交叉核对**这一整段，最后由模型写结论。

**明确的非目标**：
- 不产出逐条速读稿（用户 2026-11-02 明确：只要整合分析）
- 不替代 `bilisum.mjs` 的单链接速读流程
- 不做「自动盯盘/定时任务」（三期再加）

## 2. 交付物形态（用户 2026-11-02 定稿）

正文直出（与速读稿的交付习惯一致），完整版落盘留档但**不发文件卡片**。结构固定：

1. **一句话结论** —— 直接回答方向问题，不和稀泥
2. **依据** —— 3–5 条，每条带来源 BV + 时间点
3. **分歧与不确定** —— 谁说了什么、为什么不采信 / 存疑
4. **数据口径与时效** —— 哪些是带货口播、哪些是实测、哪些可能已过期
5. **来源清单** —— UP + 粉丝数 + 播放 + 发布时间 + 链接
6. **想对我说的话** —— 一段私话，不复述结论、不写客服腔（沿用速读稿第⑤块的口径）

## 3. 流水线

```
输入方向句
  └→ ① 拆题：模型给出 3–5 组关键词查询（含同义词/黑话/涨跌两个面）
  └→ ② 检索：每组 query × {totalrank, pubdate} 各取 1 页 20 条 → 去重
  └→ ③ 信源侦察（2026-11-02 改版，见第 4.5 节）
        · 候选池按 UP 聚合 → 逐个拉主页投稿 → 算垂直度/更新节奏/数据合理性
        · 输出 A 档（专业源）/ B 档（相关权威源）/ 被挡原因
        · **停下来等用户确认信源**（信源是用户的选择，不是工具的选择）
  └→ ④ 选片：只在确认过的 UP 的投稿里，按方向 + 时效筛（每位上限随信源数放宽）
  └→ ⑤ 打分：时效 / 权威度 / 信息密度 / 相关度 − 商单与标题党惩罚
  └→ ⑥ 取稿：缓存优先 → 字幕优先 → ASR 兜底
  └→ ⑦ 抽帧：扫逐字稿触发词 → ffmpeg 截该时刻画面 → 模型读图
  └→ ⑧ 合成：模型读 N 份逐字稿 + 帧图 → 写第 2 节的六块报告
```

工具（`research.mjs`）只负责 ①②③④⑤⑥⑦ 中"取数据"的部分，⑧ 由对话中的模型完成。

**两阶段 CLI**：

```powershell
# 阶段一：只定信源，不取稿
node research.mjs "<方向句>" --kind price --recon --keywords "词1|词2|词3" --json
# 阶段二（用户确认后）：只看确认过的信源
node research.mjs "<方向句>" --kind price --ups "mid1,mid2" --pick 3 --keywords "..." --json
```

## 4. 检索层

### 4.1 接口与硬约束（已实测）

| 项 | 结论 |
|---|---|
| 接口 | `GET https://api.bilibili.com/x/web-interface/search/type?search_type=video&keyword=<urlencoded>&page=1&order=<totalrank\|pubdate>` |
| 鉴权 | cookie 非必需但**强烈建议**：带 `cache/cookies.txt` 时实测 `code=0` 稳定 |
| 必备头 | `User-Agent`（桌面 Chrome）、`Referer: https://search.bilibili.com/all?keyword=<q>`、`Origin`、`Accept: application/json`、`Cookie` |
| 坑 | 不带头/被风控时**返回 HTML 而不是 JSON**（实测遇到），必须检测非 JSON 并退避重试 |
| 风控 | 短时间连打会 412/HTML；重试 4 次，间隔 1.2s 递增；B 站必须直连（清代理 + `NO_PROXY=*`） |
| 结果字段 | `bvid, aid, title, author, mid, typename, play, like, favorites, review(评论数), video_review(弹幕), pubdate, duration("7:14"), description, badgepay(商单), subtitle(可用性提示) |

`title` 带 `<em class="keyword">` 高亮标签，需剥成纯文本。

### 4.2 排序组合

- `totalrank`（综合）：抓到"有热度、被认可"的内容，但可能陈旧
- `pubdate`（最新）：抓时效，但前几条常是几播放的小号标题党
- 两个排序合并去重，能同时覆盖"权威老片"和"新鲜资讯"

### 4.3 打分公式

对每条候选计算 0–100 分，权重可在代码顶部常量里调：

```
score =
  35 × recency(pubdate)        // 见 4.4 时效档
+ 20 × authority              // 0.6×log10_fan + 0.4×(play/fan 比) 归一
+ 15 × engagement             // (like/play 与 reply/play，取对数归一)
+ 15 × relevance              // 标题命中关键词数 / 关键词总数
+ 10 × duration_fit           // 3–20 分钟满分；<3 分钟或 >45 分钟衰减
+  5 × channel_presence       // 同一 UP 在候选池里出现 ≥2 次（垂类常驻）
− 25 × is_promo               // badgepay=1 或标题/简介含"带货/下单/链接/优惠券"
− 30 × is_clickbait           // 标题含"震惊/哭了/必买/速看"且播放 < 阈值
− 20 × low_play               // 播放 < 2000（资讯短报类可豁免，见下）
```

**豁免规则（重要）**：2–4 分钟的「日报/资讯」类视频天然播放低于长视频，若 `typename=数码` 且标题含日期（如"11月2日"），`low_play` 惩罚减半 —— 时效性内容的价值不在播放量。

### 4.4 时效档

| 方向类型 | 窗口 | 说明 |
|---|---|---|
| 价格 / 行情 / 新品 | 近 7 天满分，7–30 天降至 0.5，>30 天 0.2 | 价格会变，旧视频是陷阱 |
| 评测 / 教程 / 科普 | 近 30 天满分，30–180 天线性衰减 | 知识衰减慢 |
| 未识别 | 按 30 天 | 保守 |

方向类型由**调用方（模型）通过 `--kind price\|review\|howto` 传入**；工具不做意图识别，避免猜错。

## 4.5 信源层（用户 2026-11-02 要求新增）

**为什么要这层**：搜索结果里"提到这个话题"和"长期专做这个话题"是两回事。前者可能是蹭热点的综合区大号，也可能是日更像搬运的带货小号；后者才是这个方向的专业 UP。判断后者必须看**主页投稿列表**。

### 4.5.1 接口（已实测）

| 项 | 结论 |
|---|---|
| 主页信息 | `GET /x/space/wbi/acc/info?mid=`（**WBI 签名**）→ 昵称、签名、认证 `official.title` |
| 投稿列表 | `GET /x/space/wbi/arc/search?mid=&ps=30&pn=1&order=pubdate`（**WBI 签名**）→ vlist[]（bvid/title/play/comment/created/length） |
| 签名 | `/x/web-interface/nav` 取 `wbi_img.img_url`+`sub_url` → 文件名即 img_key/sub_key → 混入表重排取前 32 位 → `md5(sortedQuery + mixinKey)` 作 `w_rid` |
| 风控 | 比搜索接口严格得多：实测连打十几个 UP 就 `code=-412 request was banned`。必须**≥2s 间隔**、失败退避 6s、连续失败别连累后续 |
| 缓存 | UP 数据落 `cache/ups/<mid>.json`，TTL 12 小时（同一方向重跑不重复请求） |

### 4.5.2 候选 UP 的挑选顺序

不能用"在搜索结果里出现的条数"排序——实测那样排，前面全是每天发十几条「低至 2337 元拿下 XX」的带货小号（粉丝两千、中位播放 133），而真正该看的赵德柱反而落选。

排序权重 = `log10(该 UP 候选里的最高播放) × 2 + min(出现次数, 6) × 0.5`，再取前 16 位逐侦察。

### 4.5.3 三个指标（缺一不可）

| 指标 | 定义 | 门槛 |
|---|---|---|
| 垂直度 | 近 30 条投稿中，标题/简介**同时命中主题词和方向意图词**的占比 | A 档 ≥ 30% |
| 连续性 | 近 90 天投稿条数 + 平均每周条数 | ≥ 4 条 / 90 天 |
| 数据合理 | 粉丝 ≥ 3000；中位播放 ≥ 2000；播放/粉丝比 0.02–2 为健康，>10 判为畸形 | 全部满足 |

**方向意图词**（`KIND_INTENT`）是垂直度的关键补充：搜「显卡价格」时，"4090 显卡烧穿了还能修好吗"主题词全中但讲的是维修，必须再命中 `价格|行情|涨|跌|降|报价|到手|缺货|供货` 这类意图词才算相关。

### 4.5.4 分档输出

- **A 档 专业源**：垂直度 ≥ 30%，且通过全部数据门槛
- **B 档 相关权威源**：垂直度 15–30%，但粉丝 ≥ 10 万且中位播放 ≥ 3 万（综合区大号偶尔深做，用于交叉参考；报告里必须标注"综合区大号，非专精"）
- **被挡原因**：把 `rejectedUps[]` 一并输出，便于向用户解释"为什么没选他"

### 4.5.5 确认门（硬规则）

工具不能等用户，所以**确认动作在对话层**：模型跑完 `--recon` 必须停下来用多选问题问用户，用户确认后才跑 `--ups`。信源是用户的选择，不是工具的选择；只确认 1 位也可以，但报告须注明"样本单一"。

## 5. 取稿层

- 复用 `cache/<BV>.transcript.md`：**已存在且文件头含 `## 视频基本信息` 就直接复用**，不重复下载/识别（当前机器上有 31 份可用缓存）。
- 复用方式：调用 `node bilisum.mjs get "<BV>"`（子进程），保持单一实现。若该 BV 已有缓存则工具应先检查，避免覆盖（覆盖不影响正确性，但浪费时间）。
- 并发：字幕路线允许 3 路并发；一旦某条转 ASR，则串行（CPU 吃满，避免互相拖死）。
- 失败处置：单条失败不拖垮整体，记为「未取得素材」，在报告第 4 块里如实说明。

## 6. 抽帧层（用户 2026-11-02 定制规则）

**不是固定间隔抽帧**，而是**逐字稿驱动**：

1. 扫逐字稿，命中下列触发词/句式，取该段开始时刻 `t`：
   - 「放在屏幕上 / 屏幕上 / 如图所示 / 如图 / 看这张图 / 这张表 / 这张价目表 / 图里 / 表格里」
   - 「数据来源 / 参考价 / 官方价 / 旗舰店价 / 京东价 / 淘宝价」
   - 「截图 / 我截了 / 给大家看一下 / 大家看这里」
2. 对每个命中点截 `t + 1.0s` 的单帧（避开转场/淡入），`ffmpeg -ss <t> -frames:v 1 -q:v 2`
3. 单条视频**最多 3 帧**（按命中时刻升序取前 3，避免刷屏与成本失控）
4. 命中但读图失败：不猜数字，报告里写「这里说图上有数据，但图看不清」
5. 抽帧结果落 `cache/frames/<BV>/<秒>.jpg`，输出 JSON 里给绝对路径，模型用 `read_image` 读

**没有命中触发词就不抽帧** —— 这是用户明确要求，也是省时间的关键。

## 7. 输出（工具侧 JSON）

`research.mjs` 打印结构化结果（`--json` 输出全量，默认打人类可读摘要）：

```json
{
  "query": "最近显卡价格",
  "kind": "price",
  "keywords": ["显卡价格 双十一", "9070XT 降价", "..."],

      "play": 679219, "duration": 434, "pubdate": 1793159012,

```

## 8. 兜底（比成功更重要）

- 候选中**可信素材不足 2 条** → 工具置 `insufficient: true`，并给出建议（放宽窗口 / 换关键词）。
- 模型侧据此**不硬凑结论**，直接如实说「这个方向近 7 天 B 站没有可信内容」。
- 全为带货口播时同样触发 `insufficient`。

## 9. 验证标准（验收）

1. `node research.mjs "最近显卡价格" --kind price --json` 能返回 ≥20 条候选，Top3 不含"6 播放小号"。
2. 对含触发词的视频能产出 ≥1 张关键帧，且帧图能读出图内文字（人工确认一次）。
3. 端到端跑「最近显卡价格」：3 条视频总耗时 ≤ 5 分钟（字幕路线 ≤ 2 分钟）。
4. 输出报告六块齐全，来源清单每个 BV 可点开。
5. 现有 `bilisum.mjs get <链接>` 速读流程行为不变（回归检查一条）。

## 10. 分期

- **MVP（本次）**：上述全部，3 条视频，字幕优先，抽帧按触发词
- **二期**：字幕判定 bug 修复（已在同批完成）、关键帧 OCR 文本落盘、结果缓存（同方向 1 小时内复用）
- **三期**：UP 白名单、定时盯盘、方向历史对比（今天 vs 上周）

## 11. 已知限制（必须写进报告，不许隐瞒）

1. **模型看不到画面**，除非触发词命中并抽帧成功；价格表若在无声展示期，会漏。
2. **B 站是舆论与经验样本，不是行情**：视频里的价格可能是单店价/带货价/过期价。
3. 搜索接口会间歇性返回 HTML，重试仍有失败可能；失败时按"素材不足"降级。
4. 未登录 cookie 时评论只有前 3 条，影响"评论区实际成交价"这类交叉验证。
